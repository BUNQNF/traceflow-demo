# TraceFlow 需求文档

## 1. 项目背景

- **项目机会/问题：** H5 项目依靠口头沟通和 Excel 台账传递需求，需求、原型、UI 与前端实现彼此脱节。需求变更后，团队无法可靠判断影响范围、责任人、版本和验收结果。
- **目标用户与使用情境：** 运营方提交或变更“2027 新年头像工坊 H5”的需求；产品经理组织分析、确认和流转；UI 设计师、前端工程师和验收方在固定职责内完成关联资产的交付与确认。
- **产品目标：** 在一个项目工作台中，让一条需求从提出、确认、原型、UI、前端实现到验收交付均可追溯；当需求变更时，能显示受影响资产、责任人和更新进度。
- **成功信号：** 演示者可从 `v1.0` 需求基线完成六阶段闭环，并将“新增主题模板自定义色彩变体”处理为 `v1.1`；评审可在系统中复现关联、审批、版本和验收证据。
- **约束：** 比赛交付为可交互的高保真 HTML Demo，要求多端稳定、关键与异常状态完整、AI 过程可感知/可控/可恢复。外部设计工具、代码仓库和部署服务不做真实集成。

## 3. 范围

### P0 必须完成

- 项目入口页同时提供“从已创建的项目继续”和“创建项目”。前者从选择框打开内置的已交付头像工坊 `v1.0`；后者进入空白表单，用户可上传初始需求文档，或填写项目名称、活动背景、活动时间轴、需求描述、核心目标和数据目标后从零创建。两种新建方式均汇合到同一份待确认需求。
- 单个“2027 新年头像工坊 H5”项目的项目总览、角色待办和阶段状态。
- 项目首页的四视图协同总览，统一展示需求、流程原型、视觉和运行四类产物的版本、完成度、风险及待处理项。
- 从需求提出、AI 分析、业务确认、原型、UI、前端到验收交付的完整纵向路径。
- 需求中心以“需求对照表”为创建需求和处理变更的默认总览，展示每条需求与关联资产、当前状态和版本。
- 需求、原型、UI、前端模块、验收用例和交付版本的双向可见关联。
- 方案资产按四视图汇集交付物，单项明确格式、版本、责任角色、关联对象、来源和查看入口；真实本地附件与为演示补齐的模拟资料必须可区分。
- `v1.0` 基线完成后，处理“新增主题模板自定义色彩变体”变更，生成 `v1.1` 并显示影响、任务、审核、版本差异和回退入口。
- 固定角色视图及动作限制；AI 输出的依据、确认、驳回、重试和失败恢复。
- 内置示例数据、本地保存、重置演示和桌面/移动端可用的关键任务。

### P1 有余力再做

- 项目筛选、排序、搜索与更细的健康度统计。
- 资产版本的并排差异视图、活动时间线筛选和交付清单导出。
- AI 建议的多轮优化、提示词展示和更丰富的风险解释。

### 明确不做

- 用户、组织、角色层级及权限配置后台：仅以固定角色视图证明权限边界。
- 真实 Figma/Git/CI/CD/消息通知集成，以及真实 AI 代码生成或外部部署。
- 多项目资源排期、多人实时编辑、评论体系、通用任务管理和生产级身份认证。

## 4. 用户与核心任务

| 用户/角色 | 使用情境 | 核心任务 | 期望结果 |
| --- | --- | --- | --- |
| 业务方 | 提出活动需求、补充背景或发起变更 | 提交需求；确认需求基线、变更范围和最终验收 | 业务诉求被准确落实，变更不会遗漏影响项 |
| 产品经理 | 串联业务、设计、研发和验收 | 分析需求、维护基线、确认影响、推动各阶段审批 | 每个产物有来源、责任人、版本和下一步 |
| UI 设计师 | 接收已确认原型或变更任务 | 提交 UI 页面/组件版本并响应驳回 | 只处理关联需求，且可明确知道改什么 |
| 前端工程师 | 接收通过审核的 UI 资产 | 提交实现模块/预览并响应驳回 | 获得准确实现范围和可验收标准 |
| 验收方 | 在发布前核对需求覆盖情况 | 通过或驳回验收，确认交付版本 | 交付内容与已确认需求一一对应 |

## 5. 功能与规则

| 规则 ID | 优先级 | 触发/前提 | 系统行为 | 边界/例外 | 验收标准 |
| --- | --- | --- | --- | --- | --- |
| `REQ-001` | `P0` | 业务方填写活动目标、受众、功能诉求并提交 | 系统创建“草稿需求”，记录提交人和时间；产品经理可见待分析项 | 未填标题、目标或核心诉求时不得提交，并在字段旁提示 | 填完必填项后可创建需求；缺任一必填项时不能进入分析 |
| `REQ-002` | `P0` | 产品经理对草稿需求发起 AI 分析 | AI 直接生成后续进入需求中心的完整 `REQ-*` 需求对照表；需求名称、说明和优先级可编辑；可新增需求、删除未冻结行、保存草稿或重新生成；原型/UI/前端/验收列只读显示“待创建” | `REQ-*` 编号保持锁定；新增行自动获得未占用编号；至少保留一条需求；跨阶段关联 ID 保留在内部数据中，不在尚未产出资产时暴露或允许编辑；AI 生成失败时保留原始需求和已保存草稿，展示重试入口，不得自动流转 | 可见完整需求对照表；可新增一行并删除任一非唯一行；四类关联列均只显示“待创建”且无输入框；编辑并保存后刷新不丢失；需求中心读取同一份数据 |
| `REQ-003` | `P0` | 产品经理提交需求对照表供关联角色审核 | 演示环境中需求方自动审核通过，屏幕正中显示“需求方已自动审核通过（演示）”浮窗，浮窗外内容轻度模糊并压暗；随后冻结需求基线 `v1.0`，生成不可覆盖的版本快照并解锁原型阶段 | 正式产品应由关联角色人工审核；Demo 的自动审核必须明确标注为演示行为 | 提交后先看到居中自动审核浮窗与背景遮罩；进入原型阶段后需求中心显示同一份已确认 `REQ-*` 表格 |
| `REQ-004` | `P0` | `v1.0` 已确认，产品经理进入原型生成 | 上游输入支持一键复制完整需求 Prompt；本阶段支持上传补充交付物或由 AI 生成三项标准草案，其中 `prototype.md` 是主要产出，必须包含带唯一状态 ID 的页面与状态表；生成后在页面下方展示每条 `REQ-*` 由“待创建”更新为“待审核”的具体流程依据 | 上传文件不替代标准产物；每条流程依据必须具体到 `prototype.md` 中一个或多个状态 ID；原型未确认前，UI 阶段仅显示“等待原型确认”；Demo 提交后依次模拟需求方与开发审核 | Prompt 可复制；上传后显示文件名；生成后同时可见 `prototype.md`、功能架构图、主流程图及每条需求对应的状态 ID；点击“提交关联角色审核”后依次看到需求方与开发审核通过提示，随后 UI 设计师获得待办 |
| `REQ-005` | `P0` | 原型已确认，UI 设计师进入 UI 设计 | 上游输入支持一键复制包含 `REQ-*`、`prototype.md` 状态 ID 与关键帧要求的设计 Prompt；系统生成或接收 `D-01` 关键帧、`D-02` 组件与视觉规范、`D-03` 切图/标注/交付链接，并记录来源、版本和审核状态；审核后提供两条明确路线：仅通过关键帧审核则进入高保真可交互原型制作，通过全部 UI 审核则直接进入实际 H5 页面制作 | 关键帧路线只冻结 `D-01`，不得将 `D-02/D-03` 标记为全量已审核；全部 UI 路线必须确认 `D-01` 至 `D-03`；被驳回的 UI 资产仅回到 UI 设计师待办，不影响已确认需求基线 | Prompt 可复制且包含需求与状态 ID；生成 UI 草案后同时看见两个审核出口；任一路线选择后写入审计并让项目总览、运行视图和下一阶段标题显示对应制作目标 |
| `REQ-006` | `P0` | UI 已审核通过，前端工程师提交实现模块及预览 | 系统记录模块、预览、关联 UI、需求和版本；产品经理可通过或驳回实现 | 未获 UI 审核通过的资产不得标记“待验收”；实现驳回后回到开发待办 | 通过实现审核后生成验收用例；模块详情可追溯 UI、原型和需求 |
| `REQ-007` | `P0` | 所有关联实现已通过，验收方执行用例 | 系统显示需求覆盖检查、用例结果和待修复项；验收通过后生成交付版本与发布包记录 | 任一必验用例失败或未执行时不得通过交付；驳回须填写原因 | `v1.0` 可显示“已交付”；驳回后能定位对应前端模块和责任人 |
| `REQ-008` | `P0` | 项目已创建后，任一固定演示角色在任意交付阶段进入项目总览 | 总览始终提供“发起需求变更”；发起人可选择业务方、产品经理、UI、前端或验收角色，填写变更标题和需求点。AI 判断功能增强、需求调整、范围缩减或缺陷修复，并从需求对照表命中受影响 `REQ-*` | AI 影响分析是可重做建议；修改标题或描述后旧分析自动作废。需求对照表尚未形成时关联原始需求，并把下游项标记为纳入后续交付，不伪造已有资产返工 | 在需求确认、原型、UI、前端、验收或已交付阶段均可进入变更协同；载入“新增主题模板自定义色彩变体”后命中 `REQ-003` 并显示变更类型、影响等级和追踪依据 |
| `REQ-009` | `P0` | AI 已完成 `CR-001` 影响分析，发起人提交变更申请 | 系统沿 `REQ-* -> prototype.md 状态 ID -> visual-spec.md/关键帧 -> FE 实现 -> AC 验收` 生成五项责任任务，覆盖需求视图、流程原型、视觉视图和运行视图；每项显示责任人、资产、关联理由和应交付内容 | 提交申请前不会通知责任人；已有资产显示“需要同步更新”，尚未生成的资产显示“纳入后续交付”。任务不能跳过同意直接提交内容 | 提交后五项任务统一显示“待同意”；产品经理负责需求和流程原型，UI 设计师负责视觉，前端工程师负责实现，验收方负责用例；总览和侧栏可继续进入同一变更单 |
| `REQ-010` | `P0` | 责任人收到自己负责的 `CR-001` 任务 | 每项任务必须先执行“同意变更”，随后才开放变更内容编辑器和附件入口；责任人填写并提交文档、设计、代码或验收更新说明。全部任务提交后标记“变更内容已齐备”，保留基线版本、目标草案、每次同意/提交和责任角色 | 任一任务内容为空时不得提交；单项提交不自动覆盖主交付阶段或原版本；正式发布与回退继续遵循原交付审核规则 | 五项任务都可独立完成“同意 -> 编辑/载入示例 -> 提交”；页面显示已同意/已提交数量、完整申请流转记录和 `v1.1` 内容齐备结果，刷新后保持 |
| `REQ-011` | `P0` | 用户以固定角色进入或切换 Demo 视图 | 系统仅展示该角色可操作的主动作；无权限动作显示只读状态及责任人，而非提供可执行入口 | 不实现账户登录、权限配置或组织层级；角色切换仅用于演示 | 业务方不能审核 UI/前端；UI 设计师不能确认需求基线；验收方不能修改代码模块 |
| `REQ-012` | `P0` | 用户完成会影响版本或交付的动作 | 系统记录操作者角色、时间、对象、前后状态和版本；刷新后恢复本地记录 | “重置演示”需二次确认，并将数据恢复到预置 `v1.0` 起点 | 可查看 `CR-001` 从提出到交付的完整审计记录；刷新后状态保持；重置后回到初始数据 |
| `REQ-013` | `P0` | 用户进入项目首页 | 系统以需求、流程原型、视觉、运行四视图展示当前项目的版本、完成度、阻塞项与待办，并可跳转至相应阶段 | 四视图仅展示当前项目的内置演示产物；不要求接入外部工具或实时同步 | 首页可同时看见四视图的状态；任一视图存在待更新或驳回项时，首页显示风险和责任角色 |
| `REQ-014` | `P0` | 业务方或产品经理进入需求中心，或 `CR-001` 进入处理阶段 | 系统默认展示“需求对照表”，按需求列出流程依据、视觉依据、前端实现、验收用例与版本状态；流程依据具体到 `prototype.md` 的状态 ID，视觉依据具体到 `visual-spec.md` 的对应状态或关键帧；用户从该总览进入新建需求、查看需求或处理变更 | 不实现跨项目筛选和自定义字段配置；创建/变更表单为总览的下钻操作 | 进入需求中心时首先可见需求对照表；已生成的流程依据显示一个或多个状态 ID；`CR-001` 确认后，表中仅受影响关联项显示“待更新” |

### 5.1 演示项目需求对照规则

- “2027 新年头像工坊 H5”示例的数据目标固定为：计划新增下载量 `600+`、拉长日均使用时长 `3-5 分钟`、计划社群新增 `200 人`。
- 初始需求在 AI 分析前只保留为原始输入，不提前伪装成结构化需求。分析完成后生成 `REQ-001` 至 `REQ-009` 的需求对照草稿，业务方与产品经理确认后冻结为 `v1.0`。
- 每条项目需求必须同时记录流程依据、视觉依据、前端实现和验收用例。流程依据采用 `prototype.md: STATE-ID`，视觉依据采用 `visual-spec.md: STATE-ID/关键帧`；下游未生成时显示“待创建”，生成后显示“待确认”，阶段审核通过后显示“已确认”或“已通过”。
- 后续 `CR-*` 影响分析以已确认需求对照表为唯一关联依据：先定位受影响的 `REQ-*`，再沿关联 ID 计算需更新的原型、UI、前端和验收资产；未命中的资产继续沿用当前版本。

## 6. 数据与真实性边界

| 数据/能力 | 来源 | 是否真实 | 存储位置 | 生命周期 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 项目与初始需求 | 用户上传/填写，或打开/载入内置头像工坊示例 | 用户输入 + 模拟提取 | 浏览器本地存储 | 重置前持续 | 默认进入项目选择/新建页；打开已有项目加载内置已交付快照，创建项目始终使用空白输入。不接入后端，上传文件只在当前浏览器演示会话中提取。 |
| 角色、资产和验收数据 | 状态机与确定性内置数据 | 模拟 | 浏览器本地存储 | 重置前持续 | 随六阶段确认动作逐步解锁，不允许越级生成或审核。 |
| `v1.0`、`v1.1` 版本与审计记录 | 用户交互生成 | 模拟 | 浏览器本地存储 | 重置前持续 | 刷新后恢复，用于证明版本追溯 |
| AI 分析、原型、UI 与实现建议 | 预置的确定性响应 | 模拟 | 内存及浏览器本地存储 | 重置前持续 | 明确标注“AI 建议”；结果可编辑、重试或丢弃 |
| 原型、UI、代码和预览链接 | 内置资产元数据 | 模拟 | 浏览器本地存储 | 重置前持续 | 仅呈现关联和版本，不宣称真实 Figma/Git/部署集成 |
| 方案资产中的本地文档与图片 | 演示案例已有文件 | 真实文件 | 本地项目目录 | 构建前 | 在页面标记“本地附件”；T6 以元数据预览弹层承接查看，不伪造外部在线预览。 |
| 方案资产中的协作、设计和发布材料 | 内置交付物元数据 | 演示模拟 | 浏览器本地存储 | 重置前持续 | 页面明确标记“演示模拟”，不得伪装为真实 Figma、蓝湖、部署或协作系统。 |

## 7. 非功能要求

- **目标设备与视口：** 桌面端以 `1440px` 为主演示视口；同时验证 `1024px`、`768px` 和 `375px`。小屏仅要求完成查看、确认、审核和验收等关键任务。
- **性能与资源限制：** 内置数据和本地交互应在普通浏览器中即时响应；AI 模拟可展示短暂加载状态，但不能依赖网络。
- **可访问性要求：** 文本与背景满足足够对比；所有图标按钮有文字或 `aria-label`；键盘焦点可见；不以颜色作为唯一状态信息。
- **安全与隐私要求：** 不输入或展示真实人员、业务、客户或凭据数据；不包含 API Key；本地数据可一键重置。
- **兼容性要求：** 在 Chromium 系浏览器稳定运行；避免依赖需联网的核心功能。

## 8. 总体验收标准

1. 以业务方角色创建需求，产品经理完成 AI 分析和确认，系统生成 `v1.0` 需求基线。
2. 产品经理、UI 设计师和前端工程师可依次完成原型、UI 和实现审核；每个资产都能向上追溯到需求。
3. 验收方仅在所有必验项通过后交付 `v1.0`。
4. 任一固定角色可在任意项目阶段从总览发起 `CR-001`；系统展示跨四视图的影响依据、责任角色与任务，申请提交后每位责任人先同意再提交负责的变更内容。
5. 五项关联任务全部提交后形成 `v1.1` 内容齐备记录；后续正式验收、交付与回退不得覆盖 `v1.0` 历史。
6. AI 生成失败、业务驳回、UI/实现驳回、验收失败和重置演示均有可理解且可恢复的处理。
7. 项目首页能够同时展示需求、流程原型、视觉和运行四视图的版本、状态、风险与待办；任一存在待更新项时有明确提示。
8. 进入需求中心时默认显示需求对照表；用户可从表中发起创建需求或处理 `CR-001`，并看到变更造成的关联资产状态变化。
